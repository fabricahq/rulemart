Rulemart

One place to find every public engineering rule, see who else uses it, and adopt it with one command. Every library and every rule gets its own page. Every rule page has one main call to action: add it to your project.

01

A thin layer over GitHub.

Rules, versions, and discussion all live on GitHub. Rulemart indexes them, adds search and stars, and never becomes a second place to edit or talk. Publishers add no new files.

02

One main action: Add to project.

Add the rule's group and stay in sync with the publisher, or fork only that rule into your project. Either way you get a prompt for your agent and a CLI command.

03

Usage comes from Git. Opinions come from people.

Public projects commit a record of every rule they use. Its Git history shows which public projects use each rule. Stars are the only thing Rulemart stores itself. Discussion happens in GitHub issues, where the rule lives.

Rulemart is to Code Rules what pkg.go.dev is to Go modules: a read-only window onto Git with search and trust signals. The difference is a feedback loop that goes back to the publisher.

The mental model

One loop: find, adopt, react, improve

Each arrow is something a user does or sees. Nothing new is invented for the Code Rules format. Rulemart reads what publishers and projects already write down.

JOURNEY 01 · DISCOVER

Find a rule for the problem you just hit

An agent keeps writing unbounded retry loops. You want a rule for that, and you'd like to see whether someone already wrote a good one.

  1. Land on Home. Search is the whole page, with technology and practice shelves below it.
  2. Type retries. Results match title, whenToRead, tags, and body text across every library.
  3. Each result shows what you need to shortlist it: who publishes it, impact, how many public projects use it, and how many stars it has.
  4. Fabrica rules carry the insignia. A filter narrows to them.
Counts, not scores: every number is something you can check, like "used by 1,284 public projects." Best match comes first, with usage and stars as tie-breakers.

JOURNEY 02 · EVALUATE

Decide whether a rule is right for you

A rule page answers three questions in order: What does it ask? Who is behind it? Who else uses it?

  1. The header shows the title, impact, and the rule's whenToRead, which is the line agents read first.
  2. Actions come in two groups. Adopt is the main job: Add to project, top right. Engage is quieter, under the title: Star and Discuss.
  3. The body is the Markdown file, rendered exactly as agents will see it.
  4. The usage panel shows only numbers Rulemart can stand behind, like the public projects using the rule. Stars stay in the header, next to the button that adds one.
  5. The tabs hold the discussion (mirrored from GitHub issues and pull requests), the public projects that use it, and the rule's versions.
  6. Versions lists only the library releases where this rule actually changed. A library tags many rules at once, so most releases leave any one rule untouched. Those empty versions are one checkbox away.
No keep rate yet: public data isn't strong enough to publish a percentage. Rulemart still records removals from Git history and shows them to the library's maintainers (journey 8).

JOURNEY 03 · ADOPT

Add it to your project

The main button on every rule page is Add to project. It opens a small dialog with two options, each with a prompt for your agent and a CLI command.

  1. Add to project offers two options. Add the group brings in the rule's whole group (Code Rules adds rules by group) and stays in sync with the publisher; you can exclude rules you don't want.
  2. Fork only this rule copies just this rule into the project, with attribution. You own it and can edit it, but it won't get updates.
  3. Each option leads with Copy prompt for agent, and shows the CLI command with a secondary Copy command button.
  4. Rulemart never writes to your repo in v1. You hand the prompt to your agent, or run the command yourself.
No "Add to library" for now. Copying rules between libraries spreads the same rule across many places. The better long-term shape is an org-wide library that imports from canonical libraries, with projects importing from it. That's listed under Later.

JOURNEY 04 · DISCUSS

Talk about a rule, on GitHub

Three weeks later, the rule makes your agent add headers to generated code. Maybe it should change, or maybe you just want to share what happened. Either way, it's a discussion.

  1. Click Discuss under the rule's title. Rulemart first shows open issues and pull requests about this rule, so you can join one instead of starting a duplicate.
  2. If none fits, Start a discussion opens GitHub's new-issue page in the library repo, already filled in with the rule and version.
  3. You submit it on GitHub, as yourself. Rulemart never needs write access to anyone's repo.
  4. The rule's Discussion tab mirrors it all: pull requests that change or mention the rule, then issues about it, each with status and comment count.
System of record: GitHub. Rulemart is a thin wrapper. It stores no comments, so there's nothing to sync or moderate, and maintainers keep working where they already do.

JOURNEY 06 · EVALUATE A LIBRARY

A library's home page

Library pages answer: Who stands behind this? What's inside? Can I use it? Anyone can add a library, so the page is explicit about where it comes from.

  1. Origin is always shown, and always from GitHub: the owner (an organization or a personal account, with GitHub's verified-domain badge if the org has one), the repository, and who added it to Rulemart.
  2. Everything else comes from the repo too: README, license from rule-library.yaml, groups, and tags. Fabrica libraries get the insignia.
  3. Groups are listed one per row, with Technologies and Practices in separate sections. Try it: tick groups in the mock and the import command updates.
  4. Versions come from tags, each with a summary of rules added, changed, or removed.

JOURNEY 07 · PUBLISH

Put your library on Rulemart

Publishing is "point at your repo." Anything the CLI's library check accepts, Rulemart accepts.

  1. Sign in with GitHub. That's the only account type.
  2. Add a library lists your libraries: your repos with a rule-library.yaml. Each shows whether it's public, private, or already on Rulemart.
  3. Pick one and click Add this library. Private libraries can't be published on Rulemart, and the list says so right on the row.
  4. Rulemart runs the same checks as code-rules library check, then creates the library's page.
  5. The page goes live. From then on Rulemart updates on every new tag. Untagged commits don't appear, so users only see releasable versions.
Anyone can add a public library, the way pkg.go.dev indexes any public module. Rulemart never hides where a library comes from: its GitHub owner, its repository, and who added it are on every page. Repo admins can claim a library to see its insights.

JOURNEY 08 · IMPROVE

The publisher closes the loop

This is the reason Rulemart exists beyond search. A maintainer can see which rules projects removed, and why when a reason was recorded, then turn that into a better next version. Principle 2, "turn lessons into lasting improvements," works across organizations.

  1. Insights lists rules by how many public projects removed them, from Git history.
  2. When the removal was an exclude or replace, the project's reason is quoted. Otherwise the row says "no reason recorded" and links to the commit.
  3. Removals are counted per version, so a maintainer can see whether a fix helped.
Maintainers only, for now. Removal counts help publishers, but aren't solid enough to show every visitor as a verdict.

JOURNEY 10 · INCLUDE PRIVATE PROJECTS (OPTIONAL)

Ask for private access plainly, and make "no" easy

Signing in with GitHub gives Rulemart your identity and your public repos, nothing more. To show private projects in My libraries, Rulemart needs a GitHub App installed on those repos. Before sending you to GitHub, it explains exactly what it will ask for and why.

  1. Dashboard shows a quiet banner: Showing public repos only. Include private projects?
  2. Rulemart's own screen lists each permission as GitHub will name it, why we need it, and what happens if you say no.
  3. Skip is a real choice, not a hidden link. Skipping keeps Rulemart on public repos only.
  4. On GitHub, you can pick Only select repositories, and you can remove the app at any time.
Private stays private. Private projects appear only in your own My libraries. They never count toward public numbers like "Used by," and no one else sees them.

The feedback model

Stars, usage, and discussion

Three things, each with one clear home. Every public number is a count Rulemart can defend, and anything about changing a rule happens on GitHub, where the rule lives.

Rulemart is the record

Stars

One click · signed in
  • One star per GitHub account per rule
  • Shown once, in the rule header, next to the Star button
  • No downvotes
  • Your stars are listed on your profile
Why no downvote: it carries no reason and invites pile-ons. If something should change, Discuss asks what.
Git is the record

Usage

Automatic · computed by Rulemart
  • Used by N+ public projects, today
  • Net change over the last 30 days
  • Removals: maintainers only, for now
Why only these: each is a count of things anyone can open and check. See what we can report reliably.
GitHub is the record

Discussion

Written · on GitHub
  • Discuss shows open issues and PRs first, then opens a pre-filled GitHub issue
  • Issues hold experiences, questions, and suggested changes alike
  • Open pull requests that change or mention the rule appear too
  • The Discussion tab mirrors all of it
Why GitHub: the rule changes through a pull request in that repo anyway. One home means no syncing, no Rulemart moderation, and no second inbox for maintainers. Rulemart stays a thin wrapper.

What usage we can report reliably

NumberShow it?
Public projects using the rule todayYes, as "N+". Counted from each project's current provenance.json on its default branch. Non-fork, non-archived repos only, one per repo. It's a floor, because Rulemart can only count projects it has found.
Net change in the last 30 daysYes. Dated from the commits that added or removed the rule, not from when Rulemart found the project, so newly found projects don't look like a sudden spike.
Projects that ever added it, all timeNo, for now. Next to "used by today" it reveals the removal count, which isn't ready to be public.
Removals and keep rateMaintainers only. Useful to publishers, but public repos may not represent private teams.
Private projectsNot visible. Maybe later, as an opt-in the CLI sends during sync.
Answering your question

Can Rulemart tell when a project added and later removed a rule?

Yes, cheaply. Code Rules tells projects to commit .code-rules/generated/provenance.json, which lists every active rule with its source repository, file, and exact commit. It has no timestamps or machine paths, so it only changes when the project's rules change. Rulemart reads that one file's Git history, not the whole repo.

1 · Find projects

Search for the file

GitHub code search for provenance.json under .code-rules/generated/, plus repos of signed-in users and projects people submit. Code search caps results, so submissions matter.

2 · Read one file's history

Only commits that touched it

Ask Git for commits that changed that path, using a clone without file contents or the GitHub commits API. A typical project has tens of these commits, not thousands.

3 · Compare rule lists

Diff each version

A rule that appears is an add; one that disappears is a removal. Rules are matched by source repository and file, so renaming a local alias isn't a removal.

4 · Stay current

Read only what's new

Remember the last commit read per project. Check each default branch with conditional requests, which cost nothing when nothing changed.

What the history showsHow it counts
The rule is listed in exclude in config.yamlRemoval, with reason. The config requires a reason for every exclusion.
A local rule now replaces itReplacement, with reason. Provenance records upstream and replacementReason, and links to the replacement.
The project stopped selecting its group or libraryRemoval, no reason. Shown with a link to the commit.
The library itself deleted the rule in a newer versionNot a removal. Rulemart checks the library's own history before blaming the project.
The whole .code-rules/ directory is gone, or the repo is archivedNot counted against any single rule. The project drops out of Used by.

Limits: only default branches and public repos are visible. Squash merges hide in-between states, which is fine because only the before and after matter. Forks are skipped so one project isn't counted twice.

Scope & risks

What ships first, and what could go wrong

First version

  • Sign in with GitHub, the only account type
  • Public libraries: anyone can add one, origin always shown, updates on every tag
  • Library, group, rule, and publisher pages, plus global search
  • Fabrica insignia on Fabrica-published rules (all rules at launch)
  • Add to project dialog: add the group or fork one rule, with agent prompts and CLI commands
  • Usage counts (used by, net 30-day change) from public projects on GitHub
  • Stars for signed-in users, and Discuss via pre-filled GitHub issues, with issues and PRs mirrored on the rule page
  • Maintainer insights: most-removed rules and their reasons
  • Feedback on Code Rules: a panel of topics, each opening an issue in fabricahq/code-rules

Later

  • Org-wide libraries that import from canonical libraries, so an org curates one library and its projects import from that, instead of copying rules around
  • Private libraries and org-only catalogs, visible only to org members
  • "Open a PR" to add a rule to your project, instead of copying a prompt or command
  • Propose an edit: edit the rule in the browser and open a pull request on GitHub, instead of an issue
  • Public removal data, once it proves reliable, and opt-in usage from private projects sent by the CLI during sync
  • Update alerts: "3 rules you use changed in v1.4.0"
  • Agent access: code-rules search and Markdown versions of each page, so agents can find rules themselves
  • Official rules from a technology's own maintainers, like the Go team, with their own badge
Public-only counts

Usage reflects open-source projects, which may differ from private teams. Always label counts "public projects."

Group ID fragmentation

techs/go and techs/golang split the cross-library pages. Show aliases rather than merging silently, and consider publishing a list of suggested group IDs.

Look-alike libraries

Anyone can add a library, so someone could name one to look official. The owner line comes from GitHub and is shown everywhere a library appears, and a library's title never replaces it.

Missing projects

GitHub code search caps results and skips some repos, so usage counts are a floor, not a census. Let people submit projects, and say "at least" where it matters.

Issue spam for maintainers

Rulemart only pre-fills issues; people submit them on GitHub themselves. It shows open issues and PRs first to prevent duplicates. If a library turns off GitHub issues, the button links to the repo instead.

Gaming usage and stars

Fake repos could inflate usage, and throwaway accounts could inflate stars. Count only non-fork repos with real commit history, and ignore stars from brand-new GitHub accounts.

Forks vs. license

Forking a rule must follow its library's license. Disable the fork option when the license forbids modification, and always write attribution.

Rulemart as a second source of truth

Rulemart must never let people edit rules in the browser. Every change goes through Git, or Rulemart becomes a second place where rules can drift.
