# Syllabus

This guide explains how to manage this project's [Fabrica Syllabus](https://code-rules.fabricahq.com) configuration and the engineering rules that guide agent work.

## Core concepts

- **Rule:** One engineering practice expressed in a Markdown file. It tells agents what to do, when it applies, and which exceptions to respect.
- **Group:** Related rules for a technology, such as `techs/go`, or a practice, such as `practices/testing`. Its description and reading cue help agents select relevant rules.
- **Library:** A versioned collection of groups in a Git repository. Projects import selected groups from libraries and can also author their own groups and rules in `.syllabus/rules/`.

## Connect your coding agent

Syllabus generates the rules, but your coding agent reads them only when its instructions say to. If `AGENTS.md`, `CLAUDE.md`, or the instruction file your agent reads doesn't already point to `.syllabus/generated/RULES.md`, add this section to it and keep its existing instructions:

```markdown
## Engineering rules

Before planning, implementing, reviewing, testing, or debugging a change:

1. Read `.syllabus/generated/RULES.md` and follow its instructions to
   select relevant groups and read their rules in full, including linked
   files and additional index pages.
2. Follow the applicable rules and their exceptions while doing the work.
3. Before finishing, check your work against those rules and run the
   relevant validation. Briefly report what you verified and any gaps.

If required rule files are unavailable or give conflicting instructions,
report the issue rather than silently skipping them or choosing a policy.
```

Commit that file with `.syllabus/`, so everyone who checks out the project gets the same instructions.

## Instructions for agents

### Managing rules

Use this guide to **manage rules**. Use `.syllabus/generated/RULES.md` to **read and apply adopted rules** when working on the project.

1. Identify the requested change: add a group or rule to this project, adopt a library, change an existing definition, or verify generated output.
2. Run the corresponding commands below. Run `syllabus project init` **from the Git repository root**. Other project commands can run from any subdirectory and use the root's `.syllabus/config.yaml`. Outside Git, run commands from the project root, the parent of `.syllabus/`.
3. Supply the project's intended metadata and guidance. The examples below illustrate command syntax; replace their values before using them in a real project.
4. Build after editing authored rules. Sync after changing a library's repository, selected groups or rules, pins, or ref. Inspect the resulting diff and resolve errors before reporting completion.
5. Run check. Exit 0 confirms that generated files match their inputs and this guide matches the installed CLI; it does not verify application code against the rules.

Human-readable output is the default. Add `--json` to any command for a structured response. JSON mode never prompts: supply all required flags. Inspect `ok`, `value`, and `error` and the process exit status. Exit 1 means operation failure, invalid inputs, or stale output; exit 2 means invalid usage; exit 130 means the command was interrupted. Use `--help` on a command for all options.

#### Add a group

Choose a technology group path such as `techs/go`, or a practice group path such as `practices/testing`. Use `description` to describe its scope and `when-to-read` to tell agents when to open it. Create a group once, before adding its rules.

```sh
syllabus project add group techs/go \
  --name 'Go' \
  --description 'Go conventions for this project.' \
  --when-to-read 'When writing or reviewing Go code.'
```

Read `.syllabus/rules/techs/go/README.md` for group authoring instructions. Confirm that `.syllabus/rules/techs/go/_group.yaml` contains the intended metadata. Authored group metadata takes precedence over imported metadata for the same group.

#### Add a rule

Choose a rule path within an existing group. If the group is missing, create it first with `syllabus project add group`; rule creation returns an error without creating the group. Supply a complete Markdown body and discovery metadata. This example creates a new body file without overwriting an existing one:

```sh
set -C
cat > return-errors.body.md <<'RULE_BODY'
# Return errors to the caller

Return a descriptive error when an operation fails. Let the caller decide whether to retry, report, or stop.
RULE_BODY
syllabus project add rule techs/go/return-errors \
  --title 'Return errors to the caller' \
  --impact HIGH \
  --impact-description 'Keep failures visible so callers can respond.' \
  --when-to-read 'When calling fallible operations.' \
  --body-file return-errors.body.md
syllabus project build
syllabus project check
```

Confirm that `.syllabus/rules/techs/go/return-errors.md` contains the complete rule and that the generated Go group includes it. The body file is an authoring input; future edits belong in the rule file. Put supporting files that several rules share in `.syllabus/assets/`, and link to them from a rule as `../../../assets/<file>`. If you omit `--body-file`, open the created Markdown file in your editor. Keep its metadata between the `---` lines; below it, write the instructions, rationale, correct and incorrect examples, and validation steps. Replace template placeholders, remove unused sections, and remove the `<!-- syllabus:draft -->` marker before building.

Follow the [rule authoring rubric](https://github.com/fabricahq/code-rules/blob/main/docs/src/content/docs/reference/rule-authoring.md). Use explicit exclusions in the configuration, optionally naming an authored rule by its rule ID as `replacedBy`, when overriding imported rules; adding an authored rule does not automatically replace an imported rule.

#### Add a source

A source is a library, or any other Git repository with skill folders. Obtain the publisher's Git repository address, the rules you intend to adopt, and the skills you intend to install. Inspect the source's guidance, skills, and license terms before adopting it. Replace this illustrative repository and selection:

```sh
syllabus project add source team \
  --repository 'https://github.com/example/engineering-rules' \
  --rules 'techs/go/*' \
  --skills skills/build-feature
syllabus project sync
syllabus project check
```

`syllabus project add source` records the declaration without fetching. `syllabus project sync` imports each selected rule's newest version from the library's releases, and every selected skill from the same library release, validates them, and installs vendor and generated files and the skills' installed copies together. It records every rule's version and every skill in `.syllabus/vendor/team/_source.json`, and later syncs take everything from that same record: to take a skill a newer library release adds, run `syllabus project update`. If any source fails, the previous complete output stays in place. Inspect the rule versions and retained terms in `.syllabus/generated/libraries/team/README.md` and `.syllabus/vendor/team/`.

Repeat `--rules` for each rule selector: a group prefix such as `techs/go/*`, which also takes rules the library adds to the group later, on `syllabus project update`, a single rule ID such as `techs/go/shared`, or a wildcard. Quote wildcards: `--rules 'techs/*'` or `--rules '*'`. Repeat `--skills` for each skill ID, such as `skills/build-feature`, or pass `--skills '*'` for every skill the source offers; supply at least one `--rules` or `--skills`. `--ref` takes the source exactly as it was at one tag, such as a library release tag `release/5`, or a full commit SHA; a repository without library releases, such as one that isn't a library, needs it. Branch names and abbreviated commits aren't supported.

#### Install skills

Sync and build install each included skill, and each skill you author in `.syllabus/skills/<name>/SKILL.md`, into every skill target that `skillTargets` in `.syllabus/config.yaml` names: `claude` for `.claude/skills/` and `agents` for `.agents/skills/`. Commit the installed copies with the rest of the project. Don't edit them: sync and build replace them, and they never replace a folder in a skill target that Syllabus didn't install. `.syllabus/generated/SKILLS.md` lists every skill, what it does, and where it's installed.

#### Keep a rule at its current version

To keep an imported rule at its version, read the version from `.syllabus/vendor/<source>/_source.json` and add a pin to that source's `rules.pins` list in `.syllabus/config.yaml`, with the reason you were given:

```yaml
rules:
  include: [techs/go/*]
  pins:
    - id: techs/go/shared
      version: "1.0.0"
      reason: Waiting on the author's response to our question.
```

Then run `syllabus project sync`. A pin can also move a rule to another published version, up or down. During an update, `--keep` writes the same pin for you.

#### Update rules

`syllabus project sync` never moves a rule to a newer version on its own. Adopt newer rule versions, new rules, and retirements only when the person you work for asks, never as part of another task. Preview the update first, then apply it:

```sh
syllabus project update
syllabus project update --yes
syllabus project check
```

The preview lists each library's changes with the summary of every version in between: `major`, `minor`, and `patch` changes, `new` rules, `retired` rules, `replaced` rules (library rules the project replaced with an authored rule), and `pinned` rules that a pin keeps where they are. Major changes, new rules, and retirements can change what the code must do: show them to the person who asked, and don't apply a major change without their consent. Without a terminal, `syllabus project update` only previews and exits 0; `--yes` applies exactly the versions that run previews, which can differ from an earlier preview if a library has published since. Add `--json` for the preview's rows in `value.sources`.

To keep a rule at its current version, add `--keep team:<rule-id> --reason '<why>'`, which writes a pin. To decline a new rule, add `--exclude team:<rule-id> --reason '<why>'`, which writes an exclusion. Name `team` to update only that library, or `team:<rule-id>` to move only that rule. The update writes pins and exclusions to `.syllabus/config.yaml` together with `vendor/` and `generated/`; review all three before committing.

#### Maintain and verify the project

- After editing authored rules, run `syllabus project build`, then `syllabus project check`. In Git repositories, both work from any subdirectory.
- After changing a library's repository, selected groups or rules, pins, or ref, run `syllabus project sync`, then `syllabus project check`. Sync imports the recorded versions of the other rules and chooses versions only for what changed; inspect the changes in `vendor/` before committing them.
- To adopt newer rule versions, run `syllabus project update` as described above; sync never does on its own, and check never writes files.
- Review configuration, authored rules, vendor snapshots, and generated output together. Keep project-specific notes in a separate file.
- Use `syllabus library --help` when authoring a separately published library. Project authoring and publisher authoring use different command trees.
