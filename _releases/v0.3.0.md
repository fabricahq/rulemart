## ✨ New Features

### A dashboard with one tab per concern

Your dashboard at `/me` now has four tabs, each showing only its own content: **My libraries** lists the libraries you and your organizations publish, with star counts, and the libraries you listed, with their state and inline Try again and Remove; **Projects** lists your repositories that use Code Rules and how many rule updates each is waiting for; **Starred rules** lists your stars; and **Account** shows your account's facts, Sign out, Sign out everywhere, and Delete your account. Lists sit in bordered cards, one muted line says what Rulemart read of GitHub and when, the tab bar scrolls sideways on a phone, and every page's footer names the release serving it. `/me/listings` now leads to My libraries. (#48)

### Only a repository's maintainers can add it

Adding a library to Rulemart now needs write access to its repository on GitHub. When you confirm a repository's address, and again when the listing is created, Rulemart checks with GitHub that your account may push to it, so the people who can fix or remove a listing are the people who own the code. The Add a library page lists your and your organizations' repositories that publish a library in a card, each linking to GitHub, with Add this library, "On Rulemart", or, for one you can't write to, why it can't be added; the URL form is for a repository the list misses. Every page that said anyone signed in could list a library now says its maintainers can, including the FAQ, the vetting page, and the privacy page. (#48)

### Deleting your account asks for your username

Delete your account now asks you to type your GitHub username exactly, in a dialog, before it deletes anything, and the server refuses any other value. Without scripts, the Account tab leads to a page that asks the same way. (#48)

### The GitHub App's webhook

When the operator routes it, the GitHub App "Rulemart by Fabrica" tells Rulemart as soon as someone installs, suspends, or uninstalls it, and Rulemart stops reading private repositories through that installation at once rather than at the next refresh. Rulemart treats each delivery as a prompt to ask GitHub for the installation's current state, acts on a delivery once however many times it arrives, and answers nothing but the webhook through the webhook's own address. The privacy page says what a delivery discards once the webhook is routed. The webhook stays off until the infrastructure routes it, as described under Deploying below. (#41)

### The worker can read GitHub as the Rulemart app

The worker, which checks listings and watches libraries for new releases, can now authenticate to GitHub as the GitHub App, minting a short-lived installation token every hour from the app's private key, instead of with a personal access token that expires within a year and has to be replaced by hand. Until the operator sets the app's variables, it keeps using the personal token exactly as before. (#44)

## Deploying

This release adds one migration, 00017, which creates the table that remembers webhook deliveries. It changes no table the previous release reads, so v0.2.1 keeps working while the migration runs, and rolling back to v0.2.1 keeps working afterwards.

Deploying needs no infrastructure change: with nothing new set, the webhook stays off and the worker keeps using its personal token. Two optional changes turn the new features on, each in the infrastructure repository and each a configuration change:

- **The webhook:** give the web function a public alias with an unsigned Function URL, route `POST /account/github/webhook` to it through CloudFront, and set `GITHUB_APP_WEBHOOK_ALIAS` to the alias's name on the web function, which infra-catalog v0.9.0's `http-lambda` and `cloudfront-function-url` modules provide. The web function answers 404 to every other request through the alias, and refuses to start if the variable names something that isn't a Lambda alias.
- **The worker as the app:** set `GITHUB_APP_ID` and `GITHUB_APP_PRIVATE_KEY_PARAMETER` on the worker, with `GITHUB_APP_INSTALLATION_ACCOUNT` optionally (`fabricahq` unless set), and let the worker read the key's parameter. The worker then ignores `GITHUB_TOKEN_PARAMETER`, and refuses to start with only some of the app's variables.
