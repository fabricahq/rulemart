## ✨ New Features

### See a library and its rules

Rulemart now shows real Code Rules libraries in place of the walking skeleton's test pages, built from each library's release tags. The home page lists the vetted libraries. A library's page shows its groups, its rules, and its latest release. A rule's page shows the rule, and a Versions tab lists each version with its release, date, change level, and summaries. Pages work in light and dark mode and at phone width. (#8, #9, #10)

### Fabrica's public rules

Rulemart now lists [fabricahq/public-rules](https://github.com/fabricahq/public-rules), Fabrica's public library of 127 rules, beside the test library [fabricahq/code-rules-test-library](https://github.com/fabricahq/code-rules-test-library). (#18)

### Libraries update automatically

When a vetted library publishes a release, Rulemart shows it within about an hour, with no operator. Every hour, the worker checks each vetted library's release tags and ingests only the libraries whose tags changed. A library that fails keeps showing its last release, and after five failed attempts its job moves to the dead-letter queue, whose alarm emails. (#13, #14)

### Canonical groups by name and icon

Pages name each group the way Code Rules' canonical group list names it, with an icon. A group that isn't on the list shows its ID with a "not canonical" flag. A library can't rename a shared group, or pass its own group off as a shared one. (#12)

### Logs for requests, jobs, and startup

- The web function logs one line for each request it serves, with the route, status, size, duration, and cache setting. It never logs a visitor's IP address, the path, the query string, or headers. CloudFront's own logs remain the record of who visits. (#15)
- The worker logs one line for each job, each batch, and each hourly check, with how long it took, so you can find slow or failing libraries in CloudWatch Logs Insights. (#14, #15)
- Both functions log `ready` when they start, or `startup failed` with the error. Every line names the release that wrote it. (#15)
- A page that crashes shows the visitor the error page, and logs its stack once. (#15)
- The "Migrate the database" workflow logs each migration it applies. (#15)

## ⬆️ Improvements

- Releases are now made with [Release Planner](https://release-planner.fabricahq.com). Merging a release pull request applies the release's database migrations to production, and only then tags and publishes the release. If the migrations fail, nothing is published, so a published release's migrations are already applied when you deploy it. (#7)
- `web.zip` and `worker.zip` are built reproducibly with [lambda-build](https://github.com/fabricahq/lambda-build), and each release attests them, so `gh attestation verify` can confirm a ZIP was built from `main`. The file names are unchanged, and `manifest.json` now uses lambda-build's format; infrastructure doesn't read it. (#7)

## ⛓️‍💥 Breaking Changes

### Database roles and migrations

This release adds four migrations, which run before it's published:

- 00002 creates the catalog's tables.
- 00003 lets `rulemart_catalog_reader` read the catalog.
- 00004 adds two optional columns to the catalog's `libraries` and `library_releases` tables.
- 00005 lets `rulemart_catalog_writer` write the catalog.

Besides the schema version, v0.0.2 reads and writes only `hello_messages`. None of the migrations changes it, and none removes anything, so v0.0.2 keeps working after they run, and rolling back to it still works. 00003 and 00005 fail unless infrastructure has created their group roles. Those roles and their logins, `rulemart_web` and `rulemart_worker`, are already applied, as are the `release` environment and the `production` environment limited to `main`.

### Infrastructure changes before deploying

This release replaces the skeleton's wiring. The worker now checks libraries on the schedule, and each function connects as its own least-privilege login instead of the database owner. [fabricahq/infra-live#16](https://github.com/fabricahq/infra-live/pull/16) makes these changes. Pin this release in it, then apply these units one at a time, in this order:

1. `jobs_queue`: a visibility timeout of 720 seconds, and the oldest-message alarm at 1,800 seconds.
2. `worker_lambda`: `DATABASE_URL_PARAMETER` set to `/rulemart/prod/worker-database-url`, so it connects as `rulemart_worker`, and permission to read only that parameter. It also needs `QUEUE_URL`, permission to send to the jobs queue, 2,048 MB of memory, and a 120-second timeout.
3. `poll_schedule`: invoke the worker instead of the web function, every hour instead of every 10 minutes.
4. `web_lambda`: `DATABASE_URL_PARAMETER` set to `/rulemart/prod/web-database-url`, so it connects as `rulemart_web`, and permission to read only that parameter. It no longer needs `QUEUE_URL` or the queue permission. Apply it after the schedule moves, because this web function rejects the schedule's event.
5. `cdn`: allow only `GET` and `HEAD`.

The skeleton's `/enqueue`, `/messages`, and `/cached` pages are gone.

[fabricahq/infra-live#17](https://github.com/fabricahq/infra-live/pull/17) sets `RULEMART_RELEASE` and `LOG_LEVEL` on both functions. Without them, log lines name the release `dev` and log at `info`. An unknown `LOG_LEVEL` stops a function at startup.

The production catalog starts empty, so the home page shows "No libraries yet." until the worker's first hourly check ingests the vetted libraries. To fill it right away, invoke the worker with the schedule's event:

```sh
aws lambda invoke --function-name rulemart-worker --cli-binary-format raw-in-base64-out \
  --payload '{"source":"schedule"}' /dev/stdout
```

That only queues a job for each vetted library, and the worker ingests them from the queue moments later. The catalog is filled once the worker's log shows `ingested library` for each one.
